# 多模型共识审核设计

## 目标

在不改造现有审校工作区结构的前提下，将现有单模型 AI 建议升级为三模型并行核验、字段级共识判定和可审计的自动通过机制。

产品目标是减少重复人工确认，同时保留原文证据、模型理由、分歧处理和撤销能力。“三模型一致”不直接等同于正确；系统必须先完成确定性规范化、原文证据校验和风险规则检查。

## 已确认的产品决策

- 支持三个独立模型配置槽位，允许相同接口下的不同模型。
- 自动审核模式至少要求两个不同模型家族，降低相关性错误。
- 共识按字段判定，不仅比较整条 JSON。
- 提供宽松、标准、严格三档共识策略。
- 提供 A 辅助审核与 B 自动审核两种运行模式。
- 项目有默认策略，高风险字段可单独覆盖为更严格的规则或禁止自动判过。
- 现有工作区、队列、原文区、字段顺序和快捷操作保持不变。
- 现有 AI 助手区升级为“共识摘要 + 可展开的三模型详情”，不增加遮挡字段的悬浮层。

## 范围

本次包含：

- 在现有模型设置中配置三个模型。
- 并行请求、独立超时、单模型重试和响应格式校验。
- 字段值规范化、原文证据命中校验和共识计算。
- A/B 审核模式、项目默认规则和字段风险覆盖。
- 共识摘要、三模型详情、分歧提示、自动判过标记和撤销入口。
- 模型原始结果、规范化结果、规则版本、最终决策和操作人的审计记录。

本次不包含：

- 通过第四个模型担任仲裁者。
- 用另一个大模型判断三个模型是否语义等价。
- 按模型权重投票或自动学习模型权重。
- 将 API Key 同步到工作区数据、浏览器存储、导出文件或 Git。
- 为多模型新建一套平行审校工作台。

## 界面设计

### 审校工作区

审校工作区保持现有布局。现有 AI 助手区改为以下信息层级：

1. 共识状态：显示本条的审核模式、共识档位、在线模型数和需人工字段数。
2. 共识摘要：按字段显示当前值、建议值、`3/3`、`2/3`、无共识或异常状态。
3. 判定依据：简要说明可通过或被阻断的原因。
4. 模型详情：默认折叠，展开后显示各模型的字段值、理由、证据原句、定位和校验状态。
5. 操作区：A 模式显示“采纳共识并下一条”；B 模式对自动判过记录显示“查看依据”和“撤销判过”。

单模型详情不以全屏悬浮层或遮挡右侧字段的抽屉呈现。宽度不足时，AI 区内容使用内部滚动和逐项折叠，不改变工作区整体网格。

### 设置页

现有“模型连接”页保持原导航位置，由单组表单扩展为三个配置槽位。每个槽位包含显示名称、API 地址、API Key、模型名、模型家族、启用状态、连接测试和单独编辑操作。

同页增加：

- 项目审核模式：A 辅助审核或 B 自动审核。
- 项目默认共识档位：宽松、标准或严格；初始值为标准。
- 自动审核的模型家族限制：固定为至少两个不同家族，第一版不开放关闭。
- 字段风险覆盖：仅列出与默认策略不同的字段，避免配置页冗长。

所有图标按钮都必须提供悬停提示、可见焦点和屏幕阅读器名称。

## 共识规则

### 确定性规范化

自动共识只使用确定性规则，不再调用大模型做语义裁决。规则包含：

- 去除首尾空格，统一连续空白、全角与半角标点。
- 将结构化布尔值、空值和枚举值转为统一表示。
- 书家、书体、文献名使用项目维护的显式别名表。
- 页码、段落和条目定位解析为结构化值后比较。
- 不使用模糊匹配把两个不同文本强行判为相同。

每次运行记录规范化规则版本。别名表变更只影响新运行，不静默改写历史判定。

### 三档策略

**宽松**

- 三个规范化字段值完全一致即生成共识。
- 理由和证据只供人工查看。
- 只适用于明确列入低风险允许清单的字段。

**标准**

- 三个规范化字段值完全一致。
- 至少两个模型提供的证据原句能在给定原文中精确命中。
- 本字段没有缺失、弃权、响应格式错误或校验器阻断。

**严格**

- 三个规范化字段值完全一致。
- 三个模型的证据原句经规范化后一致，并都能在原文中精确命中。
- 三个模型的页码、段落或条目定位结构化结果一致。
- 三个模型请求都完成且无弃权。

`2/3` 和其他分歧可作为人工审核的多数意见，但在 A/B 任一模式下都不能自动采纳或自动判过。

## A/B 审核模式

### A 辅助审核

- 满足字段策略的 `3/3` 共识字段自动标记为已采纳。
- 分歧、证据异常或模型失败字段保留为待人工。
- 整条记录始终需要审校员执行最终确认。
- 快捷操作可在确认后直接进入下一条，不增加二次成功弹窗。

### B 自动审核

只有同时满足以下全部条件时，才可把整条记录标记为已审：

1. 三个模型都请求成功，且至少来自两个不同模型家族。
2. 所有必填字段都满足其当前生效的共识策略。
3. 不存在 `2/3`、无共识、弃权、格式错误、证据异常或阻断性校验错误。
4. 没有字段被配置为“必须人工确认”。
5. 本次运行所使用的规则、模型配置和输出快照均已成功写入审计记录。

任一条件不满足时，记录进入人工队列，并显示具体阻断原因。B 模式不使用多数投票降级自动判过。

## 系统边界

实现拆分为四个单一职责模块：

### `ModelRunner`

读取一个模型槽位，生成请求，调用兼容 Chat Completions 的接口，并返回统一的成功或失败结果。三个实例并行运行，互不修改对方状态。

### `ResultNormalizer`

校验输出 schema，对字段值和定位做确定性规范化，校验证据原句是否在输入原文中命中。该模块不知道 A/B 审核模式。

### `ConsensusEngine`

接收三份已规范化结果和字段规则，为每个字段输出共识状态、建议值、证据状态和阻断原因。该模块不直接修改主表。

### `DecisionRouter`

结合 A/B 模式、必填字段、风险覆盖、模型家族和审计写入状态，输出 `adopt_fields`、`needs_human_review` 或 `auto_approve_record`。主表更新只由该层触发。

## 服务端接口

### 模型配置

保留已有 `GET /api/model-config`、`POST /api/model-config/test`、`PUT /api/model-config` 和 `DELETE /api/model-config` 的单槽位兼容行为，并扩展为支持三个 profile。缺少 profile 参数的旧请求默认操作第一个槽位。

公开响应对每个 profile 只返回：

- `id`、`displayName`、`apiUrl`、`model`、`modelFamily`、`enabled`。
- `configured`、`source`、`keyHint`、`lastTestedAt`、`latencyMs`、`health`。

完整 API Key 永不返回前端。

### `POST /api/ai/consensus`

请求包含记录标识、原文与定位上下文、当前字段、需校验的字段集、审核模式、项目策略和字段覆盖。服务端生成幂等的 `runId`，相同 `runId` 不重复执行或写入。

响应包含：

- `runId`、`status`、`startedAt`、`completedAt`。
- 三个模型的成功、失败、耗时和可公开配置信息。
- 各模型的字段输出、理由、证据和定位。
- 每个字段的共识状态、建议值、生效策略和阻断原因。
- `decision`：`adopt_fields`、`needs_human_review` 或 `auto_approve_record`。
- 审计记录的引用标识。

已有 `POST /api/ai/extract` 保留，继续使用第一个活动模型。这保证纯静态前端、单模型配置和现有测试不会因升级立即失效。

### 单模型重试

`POST /api/ai/consensus/{runId}/retry/{profileId}` 只重试指定模型，保留其他已成功结果，然后重新运行规范化和共识计算。重试会生成新快照版本，不覆盖旧响应。

## 执行与错误处理

- 三个模型请求并行发送，每个请求有独立超时和错误状态。
- 整体耗时不应串行叠加；以最慢的未超时模型为主。
- 第一版不在同一运行内自动重试，避免不可见的重复计费；由用户对失败槽位执行单独重试。
- 任一模型超时、返回非 JSON、schema 不合格、缺失必要字段或明确弃权时，本条禁止 B 模式自动判过。
- 部分成功结果依然可展示给人工，但不得冒充 `3/3` 共识。
- 401/403、429、超时、网络错误、响应过大和解析错误转换为简洁中文状态，不将第三方完整响应或密钥返回浏览器。

## 审计与撤销

每次共识运行保存：

- 输入记录和原文上下文的稳定摘要。
- 三个模型的公开配置快照和原始输出，不包含 API Key。
- 规范化后的字段值、证据校验结果和规范化规则版本。
- 项目策略、字段覆盖、最终决策、阻断原因、操作人和时间。
- 自动判过前后的记录快照。

撤销操作将自动判过记录恢复为待审，保留原共识运行和撤销原因。修改配置、别名表或字段规则不能静默改写历史判定。

## 安全、权限与成本

- API Key 沿用现有服务端密钥边界，不进入 `localStorage`、`sessionStorage`、IndexedDB、CSV、JSON 导出、审计记录或 Git。
- 模型配置的新增、修改、删除和 B 模式开启均属于项目管理员权限。
- 普通审校员可查看公开配置信息、模型结果和审计记录，不能读取密钥。
- 发起三模型运行前显示活动模型数和本次请求数。不在第一版引入复杂的 token 成本预测。
- 重复点击、页面刷新和网络重放通过 `runId` 幂等保护避免重复调用。

## 分阶段启用

1. 首先上线三模型运行、共识摘要和 A 辅助审核。
2. 对已完成人工审核的历史记录做离线回放，不修改主表。
3. B 模式的启用门槛为：至少回放 200 条完整记录，在符合自动判过条件的子集上达到不低于 99.5% 的整条精确率，并且书家归属、原文出处和页码定位三类高风险字段不出现错误通过。
4. 达标后由项目管理员显式开启 B 模式，默认仍为 A 模式。
5. 上线后持续抽检自动判过记录。任一高风险字段发生错误通过时，立即关闭 B 模式并回退到 A 模式，直到规则修正且重新回放达标。

## 测试设计

### 单元测试

- 字符、枚举、布尔、页码定位和显式别名的规范化。
- 证据原句精确命中、未命中、重复命中和超出输入边界。
- 宽松、标准和严格策略下的 `3/3`、`2/3`、无共识和弃权。
- A/B 模式、必填字段、字段风险覆盖和模型家族限制的决策组合。
- `runId` 幂等、单模型重试和审计版本追加。

### 集成测试

- 三模型并行成功并生成完整共识。
- 一个模型超时、鉴权失败、限流、非 JSON 响应和 schema 不合格。
- 部分成功结果可展示，但不产生自动判过。
- 单模型重试不重新调用其他已成功模型。
- 审计写入失败时不更新主表。
- 撤销恢复待审状态，不删除原共识快照。

### 前端与端到端测试

- 现有工作区网格、原文置顶、队列、快捷键和下一条操作不回归。
- 共识摘要在不展开模型详情时即可完成主要审校。
- 三模型详情折叠与展开不改变工作区整体宽度，不遮挡字段。
- A 模式不会未经用户确认把整条标记为已审。
- B 模式对全部通过记录自动完成，对任意异常记录转人工队列。
- 配置、测试、停用、重试、撤销和历史查看状态明确。
- 桌面和移动视口无重叠、无不必要横向滚动，图标按钮具有悬停提示和键盘焦点。

## 验收标准

- 三个模型实际并行调用，正常情况下总耗时不得等于三次请求耗时之和。
- 共识结果能精确说明每个字段为什么通过或被阻断。
- `2/3` 、任一模型失败、证据未命中和必填字段缺失均不能触发 B 模式自动判过。
- A 模式必须保留整条人工确认；B 模式必须有明确启用门槛、审计记录和撤销能力。
- 三个模型配置可分别测试、启用、停用和更新，完整 API Key 不离开服务端。
- 新功能不改变现有工作区主体结构，单模型接口和原有人工审校仍可用。
