# 书论工作区产品目标与路线

Review date: 2026-09-04

## 产品定位

书论工作区是一个面向书论材料整理、审校、回检和成果导出的生产型工作台。

它不是资料展示站、普通 CSV 查看器、学术门户或后台管理系统。它的核心价值是把分散、混乱、半自动生成的书论整理结果，转化为可审校、可追溯、可协作、可交付的统一主表。

## 核心目标

让用户导入一批原始数据和原文材料后，能够在同一套工作流中完成：

```text
原始材料导入 -> 自动拆块 -> 原文定位 -> 统一主表 -> 人工审校 -> 问题标注 -> 回检修订 -> 成果导出
```

最终交付物不是过程页面，而是一份可信的统一整理成果，并且每条结论都能追溯到原文、审校动作和问题处理记录。

## 目标用户

- 研究者：关注材料来源、原文定位、字段可信度和最终成果质量。
- 审校员：需要快速处理队列、确认条目、标注问题、跳到下一条。
- 项目负责人：需要查看整体进度、风险摘要、数据质量和团队分工。
- 协作者：只处理自己权限范围内的数据，不能误读或误改其他团队项目。

## 核心原则

- 少废话：界面只保留当前工作必需的信息，非关键内容折叠或进入侧窗。
- 高密度：主工作台服务扫描、比较和连续处理，不做营销式页面。
- 一体化：多份 CSV 和原文材料进入同一张统一主表，而不是割裂成多个页面。
- 快速审校：确认、标注、跳转、搜索、回检要围绕键盘和短路径设计。
- 可追溯：每条修改、确认、批注、导出都应有来源和时间记录。
- 可协作：云端部署后按团队、项目、工作区隔离数据。
- 可回滚：自动处理结果不能覆盖人工判断，关键动作应能回看与修订。

## 非目标

- 不做大而全的知识库系统。
- 不做面向访客的内容展示门户。
- 不优先做复杂排版、动效或装饰性视觉。
- 不把所有字段同时摊开在一屏里。
- 不把外部搜索结果直接当作证据，只作为查证辅助。
- 不把本地 `localStorage` 当作团队协作的真实数据源。

## 核心对象

| 对象 | 含义 |
| --- | --- |
| 团队 | 云端用户隔离边界。不同团队不能互看数据。 |
| 项目 | 一组书论整理任务，例如某本书、某批材料或某个研究主题。 |
| 工作区 | 一个项目下的一轮整理流程，包含主表、原文页、审校状态和日志。 |
| 材料 | 导入的 CSV、原文页、摘录文件或其他来源文件。 |
| 统一主表 | 工作流中的核心表，所有导入结果最终归并到这里。 |
| 条目 | 主表中的一行，可被定位、审校、标注、回检和导出。 |
| 问题标签 | 人工或系统给条目标记的问题类型。 |
| 回检队列 | 从主表中抽出的待复核条目集合。 |
| 审校事件 | 对条目的确认、修改、标注、批注、删除等动作记录。 |

## 工作流模块

### 1. 首页工作台

首页只展示项目级状态和入口：

- 当前项目
- 总体进度
- 数据质量
- 当前队列
- 风险摘要
- 最近动作
- 进入各功能区的短入口

首页不承载具体审校字段，不放长说明。

### 2. 材料导入

目标是把多份 CSV 和原文材料统一整理成一个工作区。

必须支持：

- 多 CSV 导入。
- 原文页或原文片段导入。
- 字段识别与映射。
- 导入批次记录。
- 导入后生成统一主表预览。

后续增强：

- 重复文件识别。
- 导入冲突提示。
- 字段模板保存。
- 原始文件归档。

### 3. 材料拆块

目标是把长材料拆成可处理的条目或片段。

必须支持：

- 按页码、段落、摘录或已有 CSV 行拆块。
- 保留来源文件、页码、原文片段。
- 每个条目带唯一 ID。

后续增强：

- 自动拆分规则编辑。
- 拆分前后对比。
- 异常块队列。

### 4. 原文定位

目标是把每条主表记录定位回原文证据。

必须支持：

- 显示原文页码。
- 显示命中片段。
- 显示证据等级：高、中、低、待复核。
- 支持一键打开对应原文上下文。

证据等级不等同于真伪结论，只表示系统目前能否把条目稳定定位到原文。

### 5. 统一主表

目标是成为所有整理结果的唯一操作中心。

必须支持：

- 搜索。
- 筛选。
- 排序。
- 标签。
- 状态。
- 批量选择。
- 行级审校入口。
- 导出当前视图或完整成果。

主表默认不展示所有字段，只展示审校决策必需字段；长字段进入详情区或抽屉。

### 6. 审校工作台

目标是让用户能连续、快速、低负担地处理条目。

必须支持：

- 当前条目详情。
- 原文证据。
- 修订字段。
- 问题标签。
- 批注。
- 确认、标疑、修改、删除。
- 下一条快捷键。
- 外部搜索辅助。

审校 UI 必须优先服务连续处理，不做过多装饰和解释文字。

### 7. 回检修订

目标是集中处理风险条目，而不是让问题散落在主表里。

必须支持：

- 按问题标签生成队列。
- 按证据等级生成队列。
- 按修改历史生成队列。
- 通过后回写主表状态。
- 记录回检原因和处理结果。

### 8. 成果导出

目标是导出可交付成果，而不是把内部过程原样倒出。

必须支持：

- 导出统一主表。
- 导出问题条目。
- 导出审校日志。
- 导出原文定位映射。
- 区分“工作草稿”和“最终成果”。

### 9. 项目设置

目标是管理项目和团队协作边界。

必须支持：

- 项目名称。
- 字段模板。
- 团队成员。
- 成员角色。
- 工作区默认规则。
- 云端同步状态。

设置页不进入日常审校主路径。

## 数据质量口径

数据质量不能只看已审数量，至少应包含：

- 定位准确率：能稳定定位到原文的条目比例。
- 入表完整率：主表关键字段不为空的比例。
- 回检通过率：进入回检队列后最终通过的比例。
- 重复率：疑似重复或已确认重复的条目比例。
- 风险密度：每百条中问题标签数量。

## 问题标签建议

第一版标签保持克制：

- 未定位
- 原文不符
- 疑似重复
- 字段缺失
- 人名/书家异常
- 书体异常
- 页码异常
- 需人工判断

后续可根据审校日志沉淀自动规则。

## 阶段路线

### M1：单人可用工作流

目标：一个人可以导入材料、审校、标注、回检、导出。

优先级：

1. 多 CSV 合并导入。
2. 字段映射确认。
3. 统一主表稳定展示。
4. 问题标签体系。
5. 回检队列。
6. 审校日志导出。

验收：

- 导入 2 份以上 CSV 后形成一张主表。
- 用户能连续审校 50 条不中断。
- 被标记问题的条目能进入回检队列。
- 导出结果包含主表和问题记录。

### M2：云端团队协作

目标：多人可以在云端按团队和项目协作。

优先级：

1. Supabase 登录。
2. 团队、项目、工作区隔离。
3. 多用户权限验证。
4. 单条审校实时保存。
5. 批量同步。
6. 邀请成员。

验收：

- 未加入团队的用户看不到项目数据。
- reviewer 可以审校但不能管理成员。
- editor 可以维护主表。
- admin 可以导入和分配。
- 审校动作能在云端追踪。

### M3：自动化辅助

目标：系统能主动发现风险并减少人工重复判断。

优先级：

1. 重复条目检测。
2. 原文定位异常检测。
3. 字段缺失检测。
4. 人名/书体词表辅助。
5. 外部搜索结果记录。
6. 可沉淀规则提示。

验收：

- 系统能自动生成风险摘要。
- 常见问题能自动进入回检队列。
- 人工处理后的规律能被记录为规则候选。

### M4：可复用文献整理平台

目标：把书论工作流抽象成可复用的文献整理生产平台。

优先级：

1. 字段模板系统。
2. 项目类型模板。
3. 导入规则模板。
4. 回检规则模板。
5. 可配置导出模板。

验收：

- 新项目可以复用旧模板。
- 非书论材料也能沿用导入、定位、审校、回检、导出链路。

## 当前最值得开发的下一步

下一步建议只做 M1，不分心做更大的平台化。

具体任务：

1. 建立统一导入模型：支持多 CSV 合并成一个内存主表。
2. 建立字段映射面板：让不同列名归并到统一字段。
3. 建立问题标签数据结构：条目可以被多标签标注。
4. 建立回检队列视图：从标签、证据等级、状态自动抽取。
5. 建立导出分层：主表、问题表、日志表分开导出。

## 已确认事实

- 当前项目已有成熟方向的工作台 UI，后续应保持现有 UI 风格，不做大幅视觉重写。
- 当前项目已有本地样例数据、审校队列、搜索代理、云端协作迁移和 Vercel 部署准备。
- 用户明确要求减少非关键内容、避免字段堆叠、必要时使用小窗口或跳转处理复杂内容。
- 用户重视真正可用的工作平台，而不是样子货。

## 假设

- 第一批真实使用场景仍以 CSV 和原文文本页为主。
- 短期内先保障单人工作流跑通，再扩展多人协作。
- 外部搜索在第一阶段只做查证辅助，不作为自动结论来源。
