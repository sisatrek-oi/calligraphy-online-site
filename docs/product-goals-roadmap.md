## 产品定位

书论工作区是一个面向书论材料整理、审校、回检和成果导出的生产型工作台。

它不是资料展示站、普通 CSV 查看器、学术门户或后台管理系统。它的核心价值是把分散、混乱、半自动生成的书论整理结果，转化为可审校、可追溯、可协作、可交付的统一主表。

## 核心目标

让用户导入一批原始数据和原文材料后，能够在同一套工作流中完成：

```text
原始材料导入 -> 自动拆块 -> 原文定位 -> 统一主表 -> 人工审校 -> 问题标注 -> 回检修订 -> 成果导出
```

最终交付物不是过程页面，而是一份可信的统一整理成果，并且每条结论都能追溯到原文、审校动作和问题处理记录。

## 目标用户

- 研究者：关注材料来源、原文定位、字段可信度和最终成果质量。
- 审校员：需要快速处理队列、确认条目、标注问题、跳到下一条。
- 项目负责人：需要查看整体进度、风险摘要、数据质量和团队分工。
- 协作者：只处理自己权限范围内的数据，不能误读或误改其他团队项目。

## 核心原则

- 少废话：界面只保留当前工作必需的信息，非关键内容折叠或进入侧窗。
- 高密度：主工作台服务扫描、比较和连续处理，不做营销式页面。
- 一体化：多份 CSV 和原文材料进入同一张统一主表，而不是割裂成多个页面。
- 快速审校：确认、标注、跳转、搜索、回检要围绕键盘和短路径设计。
- 可追溯：每条修改、确认、批注、导出都应有来源和时间记录。
- 可协作：云端部署后按团队、项目、工作区隔离数据。
- 可回滚：自动处理结果不能覆盖人工判断，关键动作应能回看与修订。

## 非目标

- 不做大而全的知识库系统。
- 不做面向访客的内容展示门户。
- 不优先做复杂排版、动效或装饰性视觉。
- 不把所有字段同时摊开在一屏里。
- 不把外部搜索结果直接当作证据，只作为查证辅助。
- 不把本地 `localStorage` 当作团队协作的真实数据源。

## 核心对象

| 对象 | 含义 |
| --- | --- |
| 团队 | 云端用户隔离边界。不同团队不能互看数据。 |
| 项目 | 一组书论整理任务，例如某本书、某批材料或某个研究主题。 |
| 工作区 | 一个项目下的一轮整理流程，包含主表、原文页、审校状态和日志。 |
| 材料 | 导入的 CSV、原文页、摘录文件或其他来源文件。 |
| 统一主表 | 工作流中的核心表，所有导入结果最终归并到这里。 |
| 条目 | 主表中的一行，可被定位、审校、标注、回检和导出。 |
| 问题标签 | 人工或系统给条目标记的问题类型。 |
| 回检队列 | 从主表中抽出的待复核条目集合。 |
| 审校事件 | 对条目的确认、修改、标注、批注、删除等动作记录。 |

## 工作流模块

### 1. 首页工作台

首页只展示项目级状态和入口：

- 当前项目
- 总体进度
- 数据质量
- 当前队列
- 风险摘要
- 最近动作
- 进入各功能区的短入口

首页不承载具体审校字段，不放长说明。

### 2. 材料导入

目标是把多份 CSV 和原文材料统一整理成一个工作区。

必须支持：

- 多 CSV 导入。
- 原文页或原文片段导入。
- 字段识别与映射。
- 导入批次记录。
- 导入后生成统一主表预览。

后续增强：

- 重复文件识别。
- 导入冲突提示。
- 字段模板保存。
- 原始文件归档。

### 3. 材料拆块

目标是把长材料拆成可处理的条目或片段。

必须支持：

- 按页码、段落、摘录或已有 CSV 行拆块。
- 保留来源文件、页码、原文片段。
- 每个条目带唯一 ID。

后续增强：

- 自动拆分规则编辑。
- 拆分前后对比。
- 异常块队列。

### 4. 原文定位

目标是把每条主表记录定位回原文证据。

必须支持：

- 显示原文页码。
- 显示命中片段。
- 显示证据等级：高、中、低、待复核。
- 支持一键打开对应原文上下文。

证据等级不等同于真伪结论，只表示系统目前能否把条目稳定定位到原文。

### 5. 统一主表

目标是成为所有整理结果的唯一操作中心。

必须支持：

- 搜索。
- 筛选。
- 排序。
- 标签。
- 状态。
- 批量选择。
- 行级审校入口。
- 导出当前视图或完整成果。

主表默认不展示所有字段，只展示审校决策必需字段；长字段进入详情区或抽屉。

### 6. 审校工作台

目标是让用户能连续、快速、低负担地处理条目。

必须支持：

- 当前条目详情。
- 原文证据。
- 修订字段。
- 问题标签。
- 批注。
- 确认、标疑、修改、删除。
- 下一条快捷键。
- 外部搜索辅助。

审校 UI 必须优先服务连续处理，不做过多装饰和解释文字。

### 7. 回检修订

目标是集中处理风险条目，而不是让问题散落在主表里。

必须支持：

- 按问题标签生成队列。
- 按证据等级生成队列。
- 按修改历史生成队列。
- 通过后回写主表状态。
- 记录回检原因和处理结果。

### 8. 成果导出

目标是导出可交付成果，而不是把内部过程原样倒出。

必须支持：

- 导出统一主表。
- 导出问题条目。
- 导出审校日志。
- 导出原文定位映射。
- 区分“工作草稿”和“最终成果”。

### 9. 项目设置

目标是管理项目和团队协作边界。

必须支持：

- 项目名称。
- 字段模板。
- 团队成员。
- 成员角色。
- 工作区默认规则。
- 云端同步状态。

设置页不进入日常审校主路径。

## 数据质量口径

数据质量不能只看已审数量，至少应包含：

- 定位准确率：能稳定定位到原文的条目比例。
- 入表完整率：主表关键字段不为空的比例。
- 回检通过率：进入回检队列后最终通过的比例。
- 重复率：疑似重复或已确认重复的条目比例。
- 风险密度：每百条中问题标签数量。

## 问题标签建议

第一版标签保持克制：

- 未定位
- 原文不符
- 疑似重复
- 字段缺失
- 人名/书家异常
- 书体异常
- 页码异常
- 需人工判断

后续可根据审校日志沉淀自动规则。

## 五个开发阶段

| 阶段 | 要开发或完善的内容 | 验收时应当做到 |
|---|---|---|
| 1. 书论版本导入与 OCR／校对 | 打通 PDF／已有 TXT → 缺页 OCR → 人工校对 → 候选抽取 → 审校入库 → 导出；原始 OCR 与人工正文分开；补失败重试、进度、重复导入处理和问题回检 | 一小批真实材料走完整条流程；每条书论可回到原扫描页；重试和重复导入不重复入库；待核实内容保留待复核状态 |
| 2. 稳定协作与数据基础 | 核查现有功能、线上迁移与登录；补齐项目成员和权限、任务领取、保存状态、修改记录、冲突处理与备份恢复；统一材料、页码、条目等编号和字段 | 5 个账号可以按权限参与同一项目；刷新后数据仍在；两人修改同一条时不静默覆盖；修改可追溯；能从备份恢复试验数据 |
| 3. 增加书法图像与图文关联 | 批量导入图片，登记作品、书家、书体、来源和重复组；支持查看、筛选、裁切区域和配对；把已审核书论拆成可检验的描述，记录适用范围，并建立描述与图片／题目的关联 | 在平台里能找到“一条描述对应哪些图片、图片来自哪个作品”；裁切图能回到原图；能建立带属性问题的 A/B 图像对，关联理由和审核状态可查 |
| 4. 建立人工标注与复核工作台 | 任务分派、独立提交、证据框、可判断／平局／看不清／有争议等标签；隐藏书论、作者和模型结果；增加分歧复核、裁决、参考答案冻结与版本记录 | 两位标注者独立作答，提交前看不到对方答案；指定复核人处理分歧；视觉答案冻结后再做文字适用性核验；可导出完整标注记录 |
| 5. 接入模型评测与结果查看 | 让模型实际接收图片与指定文字；可配置无书论、相关书论、干扰文字等条件；记录模型、提示、题库版本和原始回答；实现批量任务、重试、费用上限、计分、对比与导出 | 同一批题能在不同文字条件下运行；每个得分可回查原始回答并重算；正确率、作答率与不确定题处理分开展示；运行异常单独记录并按预设规则处理 |

这些阶段按交付能力划分，不是五个等时长任务。单人开发时，可在阶段 1 确定字段时预留阶段 3 的关联需求；阶段 4 依赖稳定的图片和题目编号；阶段 5 可先用开发样例调通接口，正式计分依赖冻结的参考答案。

## 当前第一阶段：版本导入与 OCR

用户于 2026-09-27 明确先完成书论版本导入与 OCR。首个交付是本地可用的材料处理与校对流程；五人账号及云协作随后单独验收。此前 6 个任务包仍作为后续清单，当前优先其中的材料、校对和端到端验收：

1. **现状盘点**：逐个验证已有页面和接口，把问题列成可复现的缺陷清单，区分已有但不可用、部分可用和真正缺失。
2. **数据库与数据保存**：确认线上迁移、统一字段与编号、导入去重、修改日志、备份恢复。
3. **账号与协作**：验证 5 人登录、加入项目、角色权限、任务领取和编辑冲突。
4. **材料与 OCR**：登记原书及页码，补缺页识别、任务进度、失败重试，记录引擎和原始输出。先比较小批真实页，再选择是否接入独立 OCR 工具。
5. **校对与审核体验**：沿用现有逐页工作台，完善原图定位、文本保存、问题标记、候选确认和回检；修复影响日常工作的交互问题。
6. **端到端验收与发布**：建议用 10 页小样本覆盖已有 TXT 复用和实际 OCR 两条路径，再走抽取、审核、导出；补操作说明并让 5 人实际试用。

先完成材料导入、OCR、校对保存和本地联调，再推进共享数据库与账号协作。10 页只是工程验收起点，不是 OCR 准确率或研究效用的统计证明。

部署继续尊重现有边界：Vercel 承载网站及适合的接口，Supabase 承载身份与持久数据，本地服务承担 PDF/OCR。第一版可以指定一个材料处理端，把结果交给共享平台；必须验证其他成员能访问所需原图和文本。若要求五人均从网页提交 OCR 并后台运行，需增设可持续运行的处理服务和任务队列，这属于单独的开发项。

## 后续功能需要提前留下的接口

- 数据关系：材料 → 原文页 → 审核条目／描述；作品 → 图片 → 题目；题目 → 独立标注／冻结答案；题目＋文字条件＋模型配置 → 运行记录与得分。
- 保存状态、原始记录、数据版本、权限与操作日志贯穿各阶段，避免增加新模块后重新追查来源。
- 现有“证据等级”表示原文可靠性，新增“模型效用”保存具体实验条件下的结果，两者分字段。
- 盲标隐藏信息应由接口权限保证，不只是前端不显示；模型作答请求不得携带人工参考答案。
- 计分规则版本化：可判题主测试中拒答和无效输出不从分母删除；诊断测试另外报告作答率、已答题正确率及不确定题的处理。网络失败、任务未完成和模型拒答分别记录，禁止只挑成功结果汇总。
